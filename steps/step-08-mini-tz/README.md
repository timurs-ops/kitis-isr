# Шаг 08 · Мини-ТЗ: «Бронирование аудитории» (клиентская версия)

**Цель:** первое самостоятельное приложение по ТЗ — репетиция профильного модуля ДЭ.
Скелетов нет: только требования. Как реализовывать — решаешь сам (это и есть экзамен).

## Техническое задание

### Роли

- **Студент** и **админ**. Аккаунты — из шага 6 (`localStorage['kitis-de:users']`).
- Роль храни в записи пользователя (`role: 'student' | 'admin'`). Админа назначаешь вручную
  через консоль браузера — для прототипа допустимо; на защите объясни, почему на сервере так нельзя.
- Не вошёл → видишь только формы входа/регистрации.

### Студент

- Форма заявки: **аудитория** (select: 104, 105, 201, 403, 109м), **дата** (input type=date),
  **пара** (select 1–6), **цель** (текст, обязательна).
- Валидация: все поля обязательны, дата не в прошлом.
- Видит **только свои** заявки: аудитория, дата, пара, цель, статус, причина отказа.

### Админ

- Видит **все** заявки всех студентов (с ФИО и email автора).
- Подтверждает / отклоняет. Отклонение — **с обязательной причиной**.

### Статусы

`новая → подтверждена` или `новая → отклонена (+причина)`. Из конечных статусов назад нельзя.

### Конфликт (главная бизнес-логика)

Нельзя **подтвердить** две заявки на одну и ту же **аудитория + дата + пара**.
При попытке — понятное сообщение («403 уже занята на 18.11, 2 пара»), статус не меняется.
Отклонённые и новые заявки не конфликтуют.

### Хранилище и интерфейс

- Всё в `localStorage['kitis-de:bookings']` (массив заявок с id).
- Адаптив: 360px и 1280px, ничего не разваливается.
- Статусы визуально различимы (цвет/плашка), не только текстом.

## Артефакт

Папка `app/` в твоём репозитории: `index.html` + css/js. Ссылка с корневой витрины «Мои работы».
`SUBMISSION.md` — обязателен, раздел «ИИ» — честно.

| # | Критерий | Балл |
|---|---|---|
| 1 | Регистрация/вход работают, роли различаются | 1 |
| 2 | Не вошёл — приложение закрыто | 0.5 |
| 3 | Форма заявки: все поля, валидация, дата не в прошлом | 1 |
| 4 | Студент видит только свои заявки | 1 |
| 5 | Админ видит все заявки с авторами | 0.5 |
| 6 | Подтверждение/отклонение работает, отказ с причиной | 1 |
| 7 | Конфликт аудитория+дата+пара ловится, сообщение понятное | 1.5 |
| 8 | Статусы визуальны, из конечных нет перехода назад | 0.5 |
| 9 | Адаптив 360/1280, консоль чистая | 0.5 |
| 10 | Код структурирован (функции, а не каша), данные не дублируются | 0.5 |
| Защита | объясни конфликт-проверку и модель данных; живая правка (добавь поле «комментарий») | 2 |

**Экспресс-трек (lite):** без админки — студент создаёт заявки и видит свои со статусом «новая»;
конфликт не требуется. Рубрика: пункты 1–4, 9, 10 + защита (пересчёт пропорционально).

## Совет

Сначала модель данных на бумаге (какие поля у заявки, как связаны с пользователем), потом формы,
потом логика статусов, в конце — красота. Ровно так же на ДЭ.
